## Engine v2: scheduling, fan-out, priority, nested recovery

Machine: Apple M1, 8 cores, 8.0 GB RAM, macOS-26.5.2-arm64-arm-64bit-Mach-O, Python 3.13.7, postgres (PostgreSQL) 16.15 in Docker Desktop. Started 2026-10-26T15:20:36-0700, took 372.6 s. Real worker processes and an isolated database; every number is derived from rows the engine wrote (attempt timestamps, `ready_at`, `queue_wait_ms`) plus `psutil` samples of the worker processes and `pg_stat_activity` samples. **No model calls are made**: nodes are aggregations and calculator tool calls, so these measure the scheduler and database, not agents. Reproduce: `cd benchmarks && uv run --group bench python engine_v2_bench.py --label engine_v2`.

The backlog (40 workflows) is pre-filled before workers start, so *start latency* is queueing delay inside the backlog, not submission delay. *Lock-wait share* is the fraction of sampled active backends waiting on a PostgreSQL lock (the per-run row lock that serializes event sequencing and state transitions). *RSS* is summed over all worker processes. Cells are repetitions interleaved over time; ranges show real run-to-run variance, so treat differences inside them as noise. The compose app containers (api, web, worker) were stopped during the run.

A backlog of priority-9 four-step chains is submitted with a few priority-0 chains. **Aging is accelerated to 0.5 s per priority point** (default 30 s) so the effect shows in a short benchmark; with aging off the low-priority runs wait for the entire backlog. The cost is the high-priority median completion shown above.
